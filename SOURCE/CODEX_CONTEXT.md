## 1. 项目一句话定义

碰碰宠物蛋是一款面向 3–10 岁儿童的离线电子宠物设备：孩子在设备中孵化并照顾一只山海灵兽，通过每天喂养、陪伴、小游戏、训练、NFC 卡牌、碰一碰联机和合作 Boss，完成从灵蛋到终极青龙的成长 Demo。

MVP-A 当前目标不是完整商业量产版，而是基于开发板完成一个可演示、可联调、可验证核心体验的离线 Demo。

---

## 2. CodeX 工作目标

CodeX 在本项目中的角色是：

1. 理解 SDK 工程结构；
2. 协助进行嵌入式 UI 页面开发；
3. 协助接入美术资源、序列帧、Sprite Sheet、动画配置与 manifest；
4. 协助实现或梳理 4 键交互、页面状态机、NFC 读卡、BLE 碰一碰、合作 Boss、本地存档与异常恢复；
5. 输出可验证的工程改动、测试说明和回归清单；
6. 不擅自扩大产品范围，不引入联网、App、云端、复杂 RPG 系统或商业版复杂卡牌系统。

## 3. 当前工程背景

### 3.1 硬件 / SDK 目标

当前开发目标按以下工程口径执行：

- 芯片 / SDK：杰理 AC701N / BR28 手表类 SDK；
- 主应用：`apps/watch`；
- UI 代码路径：`apps/watch/ui/lcd/STYLE_WATCH_NEW`；
- UI 资源工程路径：`cpu/br28/tools/UI工程/ui_454x454_watch`；
- 板级配置：`CONFIG_BOARD_701N_DEMO`；
- Demo 离线运行；
- 不依赖 App；
- 不依赖云端；
- 不依赖联网；
- 不依赖 OTA。

### 3.2 标准硬件交互口径

MVP-A / 当前 SDK Demo 只围绕以下输入与硬件能力设计：

- 4 个物理按键：上 / 下 / 确认 / 返回；
- 长按确认：唤醒 / 重要确认 / 蓄力；
- 长按返回：回首页 / 退出二次确认；
- 摇一摇：唤醒、互动、QTE 或蓄力；
- 顶部 NFC：卡牌读取、碰一碰近距离触发；
- BLE：持续联机通信、对战 / 合作 Boss 指令同步；
- 本地存储：设备卡包、本地设置、异常恢复；
- SD / 内容卡口径：MVP-A 可按当前工程和 Demo 需要保留“当前宠物 / 世界内容来源”的抽象，不强制实现完整商业版 SD 卡系统。

### 3.3 明确不做

CodeX 不应主动引入以下内容：

- 手机 App；
- 云端账号；
- 云同步；
- Wi-Fi；
- 麦克风；
- 摄像头；
- 触摸屏交互；
- 滑盖交互；
- 线上商城；
- 充值；
- 排行榜；
- 复杂多人在线；
- 多宠物完整管理；
- 完整商业版卡牌经济；
- 二级交易；
- 套装战力奖励；
- 复杂 TCG 规则；
- 高复杂度 RPG 属性，如速度、暴击、职业、技能树、回复、控制等。

## 4. MVP-A 当前产品范围

MVP-A 是开发板 Demo，目标是把最核心的“养成 + 4 键 UI + NFC + BLE + 合作 Boss + 存档”跑通。

### 4.1 必须覆盖的主线

1. 山海灵蛋唤醒；
2. Stage0–Stage5 青龙成长；
3. 4 键家园交互；
4. NFC 读卡入卡包；
5. 两台设备碰一碰触发 BLE；
6. 合作岩灵 Boss；
7. 本地存档与异常恢复；
8. 基础工程调试页或调试入口。

### 4.2 MVP-A 宠物成长阶段

MVP-A 以青龙单宠主线为主：

- Stage0：灵核 / 灵蛋；
- Stage1：包子幼体，不能出现龙角、鳞片、青绿属性等可识别青龙特征；
- Stage2：灵木成长期，可以出现属性倾向；
- Stage3：灵茧；
- Stage4：青龙宝宝；
- Stage5：终极青龙。

注意：完整 PRD 中有 18 只灵兽池，但 MVP-A 不需要实现完整 18 只灵兽，只需要以青龙主线验证成长、资源、动画、UI、存档和玩法闭环。

### 4.3 MVP-A 玩法范围

当前 Demo 建议覆盖：

- 唤醒；
- 首页 / 家园；
- 基础状态展示；
- 每日照料入口；
- 喂食；
- 陪伴；
- 睡觉 / 休息；
- 训练；
- NFC 卡牌读取；
- 卡包展示；
- 碰一碰联机；
- 合作岩灵 Boss；
- Boss QTE；
- 胜利 / 失败 / 奖励；
- 存档恢复；
- 异常提示。

### 4.4 暂缓内容

MVP-A 不做：

- 完整 1v1 商业对战；
- 2v2 对战；
- 多宠物完整系统；
- 完整卡牌包商品系统；
- 家园卡完整布置；
- 18 只灵兽全部成长；
- 完整 SD 内容卡商品化系统；
- 图鉴；
- 线上账号；
- 家长 App；
- 排行榜。

## 5. UI 工程约束

### 5.1 屏幕与画布

- 主设计画布：454×454；
- 可兼容导出 / 检查：360×360；
- 目标屏幕：1.5 英寸圆形或近圆形彩屏；
- 视觉设计必须考虑圆屏安全区；
- 不能把关键信息压到四角；
- 文案必须短；
- 页面必须高度图形化。

### 5.2 页面结构原则

每页尽量遵守：

- 顶部：短标题，2–6 个中文字符；
- 中央：唯一主视觉，如宠物、蛋、卡牌、Boss、状态动画；
- 底部：唯一操作气泡；
- 不做多按钮并列；
- 不做手机式 Tab；
- 不做长列表；
- 不做触摸拖拽；
- 关键操作必须能用 4 键完成。

### 5.3 4 键交互原则

默认映射：

- 上：菜单上移 / 切换上一个；
- 下：菜单下移 / 切换下一个；
- 确认：进入 / 选择 / 使用 / QTE 点击；
- 返回：返回上级 / 取消 / 退出；
- 长按确认：唤醒 / 蓄力 / 重要确认；
- 长按返回：回首页 / 退出战斗需二次确认。

## 6. 核心系统设计口径

### 6.1 宠物成长

MVP-A 采用简化成长闭环：

```text
唤醒灵蛋
→ 完成照料 / 训练 / 互动
→ 提升成长进度
→ Stage 推进
→ Stage2 属性倾向
→ Stage3 灵茧
→ Stage4 青龙宝宝
→ Stage5 终极青龙
→ 合作 Boss / 展示 / 继续互动
```

养成系统强调：

- 不设计宠物死亡；
- 长期未照料可以进入沉睡；
- 沉睡后可通过唤醒、喂食、安抚、灵核修复恢复；
- 不做外观惩罚；
- 通过心情、健康、成长速度和反馈表达照料质量。

### 6.2 属性因子

完整产品有灵木 / 烈火 / 玄水三属性。MVP-A 以青龙 / 灵木为主，但工程变量和数据结构可保留三属性扩展位：

- `WoodFactor`：灵木；
- `FireFactor`：烈火；
- `WaterFactor`：玄水。

属性只做：

- 视觉差异；
- 成长方向；
- 对战克制；
- 反馈文案。

属性不做：

- 天然攻击高低；
- 天然防御高低；
- 天然速度；
- 暴击；
- 回复；
- 控制；
- 职业定位。

### 6.3 级别系数

完整产品中 `LevelCoefficient` 代表成长质量。MVP-A 可以简化为成长质量或亲密成长加成，用于：

- 成长进度微调；
- 亲密动画触发；
- Boss / 训练表现；
- 后续扩展。

不要让付费卡或单次操作无限堆高数值。

### 6.4 NFC

MVP-A NFC 目标：

- 真实读取 NFC Tag；
- 识别卡牌类型；
- 将卡牌写入设备卡包或 Demo 卡包；
- 播放读取动画；
- 已读 / 错误 / 中断要有明确提示。

NFC 在联机中只负责近距离触发和配对确认，不传输战斗持续数据。

### 6.5 BLE

MVP-A BLE 目标：

- 两台设备通过碰一碰进入连接流程；
- BLE 建连；
- 交换基础状态；
- 合作岩灵 Boss 指令同步；
- 双端本地计算或同步必要战斗状态；
- 断线时回到安全状态。

### 6.6 本地存档

MVP-A 必须避免关键数据丢失：

- 当前 Stage；
- 成长进度；
- 当前宠物状态；
- 已获得卡牌；
- Boss / 训练关键结果；
- 异常恢复标记。

关键写入应考虑：

- 低电；
- 写入中断；
- 重启恢复；
- 数据版本；
- 校验和或简单校验；
- 备份区或双份保存。

## 8. CodeX 执行规则

### 8.1 每个任务开始前

CodeX 应先读取：

1. `sdk/source/CODEX_CONTEXT.md`；
2. `sdk/source/SOURCE_INDEX.md`；
3. 与任务相关的专题文件。

### 8.2 改代码前

必须先输出：

### 8.3 禁止行为

- 不要在未确认构建入口前大规模改 SDK；
- 不要改无关模块；
- 不要把大型美术资源直接塞进代码目录；
- 不要把 `source/` 加入固件编译；
- 不要提交构建产物；
- 不要删除 SDK 原有文件；
- 不要重命名核心目录；
- 不要把商业版复杂规则误带入 MVP-A。

### 8.4 输出格式

每次任务完成后至少输出：

1. 修改文件列表；
2. 新增文件列表；
3. 未修改但检查过的文件；
4. 本次实现内容；
5. 未完成事项；
6. 测试 / 验证结果；
7. 后续建议；
8. 建议 commit message。

## 10. 当前最重要的工程判断

1. MVP-A 是开发板 Demo，不是完整商业版。
2. 单宠青龙主线优先于完整 18 灵兽系统。
3. 4 键交互优先于复杂 UI。
4. 圆屏可读性优先于信息完整度。
5. NFC / BLE 技术验证优先于完整卡牌经济。
6. 本地存档稳定性优先于玩法复杂度。
7. `source/` 是 CodeX 知识库，不参与编译。
8. 遇到 PRD 冲突时，应先查 `open_questions_and_conflicts.md`。
