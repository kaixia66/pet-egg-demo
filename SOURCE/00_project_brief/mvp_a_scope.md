# MVP-A Scope

> 本文件用于锁定碰碰宠物蛋 MVP-A 开发板 Demo 的执行范围。  
> 当完整 PRD、商业版设想、UI 设计稿、资源生成计划与 MVP-A 发生冲突时，CodeX 应优先遵守本文件。

---

## 1. MVP-A 定义

MVP-A 是一个基于开发板的核心玩法 Demo，不是量产商业版。

目标是用最小但完整的工程闭环验证：

1. 离线电子宠物能否在开发板上稳定运行；
2. 4 键圆屏 UI 是否可用；
3. 青龙从 Stage0 到 Stage5 的成长主线是否可演示；
4. NFC 读卡入卡包是否能跑通；
5. 两台设备碰一碰后是否能通过 BLE 进入合作玩法；
6. 合作岩灵 Boss 是否能通过本地交互和同步完成；
7. 本地存档与异常恢复是否可靠。

---

## 2. MVP-A 一句话目标

在杰理 AC701N / BR28 开发板上完成一个离线运行的“山海灵蛋唤醒 → 青龙成长 → 4 键家园交互 → NFC 读卡 → 碰一碰 BLE → 合作岩灵 Boss → 本地存档恢复”可演示 Demo。

---

## 3. 工程目标环境

MVP-A 按以下工程环境执行：

- 芯片 / SDK：杰理 AC701N / BR28 手表类 SDK；
- 主应用：`apps/watch`；
- UI 代码路径：`apps/watch/ui/lcd/STYLE_WATCH_NEW`；
- UI 资源工程路径：`cpu/br28/tools/UI工程/ui_454x454_watch`；
- 板级配置：`CONFIG_BOARD_701N_DEMO`；
- 运行方式：离线运行；
- 依赖限制：不依赖 App、云端、联网、OTA。

---

## 4. MVP-A 产品主线

### 4.1 主体验闭环

```text
开机 / 唤醒
→ 山海灵蛋出现
→ Stage0 灵核
→ Stage1 包子幼体
→ Stage2 灵木成长期
→ Stage3 灵茧
→ Stage4 青龙宝宝
→ Stage5 终极青龙
→ NFC 读卡入卡包
→ 碰一碰连接朋友设备
→ 合作岩灵 Boss
→ 奖励 / 结果
→ 本地存档
→ 异常恢复
```

### 4.2 用户感知

孩子看到的是：

- 我发现了一颗山海灵蛋；
- 我每天照顾它；
- 它会成长；
- 它变成了青龙；
- 我可以刷卡获得道具；
- 我可以和朋友碰一碰；
- 我们可以一起打岩灵 Boss；
- 我的成长和结果会被保存。

## 5. MVP-A 必做范围

### 5.1 启动与唤醒

必须做：

- 开机 / 启动 Logo；
- 山海灵蛋发现；
- 首次唤醒；
- 长按确认或确认键触发；
- 顶部能量核心 / 能量注入视觉；
- 进入 Stage0。

可简化：

- 不做完整新手教程；
- 不做复杂设置流程；
- 不做用户账号。

### 5.2 青龙成长 Stage0–Stage5

必须做：

| Stage | 名称 | MVP-A 表现要求 |
|---|---|---|
| Stage0 | 灵核 / 灵蛋 | 生命光点、灵蛋、心跳、苏醒感 |
| Stage1 | 包子幼体 | 圆润、可爱、不能暴露龙特征 |
| Stage2 | 灵木成长期 | 出现灵木属性倾向，但不完全揭晓青龙终态 |
| Stage3 | 灵茧 | 茧形、等待、成长仪式 |
| Stage4 | 青龙宝宝 | 明确揭晓小青龙 |
| Stage5 | 终极青龙 | 华丽终极形态，可用于展示 / Boss |

必须支持：

- 当前 Stage 展示；
- 成长进度；
- 测试模式快速成长；
- Stage 切换动画或过渡页；
- Stage 数据本地保存。

暂不做：

- 18 只灵兽完整随机池；
- 多宠物；
- 复杂稀有度抽取；
- 复杂属性分支。

### 5.3 家园 / 首页交互

必须做：

- 宠物首页；
- 当前宠物显示；
- 简化状态显示；
- 4 键菜单；
- 喂食入口；
- 陪伴入口；
- 训练入口；
- 卡包入口；
- 联机 / Boss 入口；
- 返回首页逻辑。

建议状态：

- 心情；
- 饱腹；
- 成长；
- 亲密或能量。

可简化：

- 不做完整健康系统；
- 不做复杂家园布置；
- 不做家具；
- 不做长列表。

### 5.4 4 键交互

必须做：

- 上 / 下：切换菜单或选项；
- 确认：进入 / 使用 / 选择；
- 返回：返回上一级；
- 长按确认：唤醒、蓄力或重要确认；
- 长按返回：回首页或退出二次确认；
- QTE 中确认键可连点或节奏输入。

必须保证：

- 所有核心流程无触摸也可完成；
- 页面层级尽量不超过 2 层；
- 儿童误操作时可返回。

### 5.5 NFC 读卡入卡包

必须做：

- 进入读卡页面；
- 提示“把卡牌贴到顶部能量核心”或类似短文案；
- 读取 NFC Tag；
- 识别至少一种 Demo 卡；
- 显示读取成功动画；
- 将卡写入设备卡包或 Demo 卡包；
- 已读 / 错误 / 中断要有提示；
- 可在卡包中看到卡牌。

MVP-A 可简化：

- 可先用 Demo UID / Tag Type；
- 不强制实现安全标签完整防复制；
- 不强制实现商业版所有卡类；
- 不强制实现卡包上限；
- 不强制实现真实实体卡写入锁定。

但必须保留接口或注释，方便后续接入安全标签、签名、UsedFlag。

### 5.6 卡包

必须做：

- 至少能展示 NFC 读取到的卡；
- 至少支持一种卡牌类型；
- 可显示卡牌名称、类型、状态；
- 可从首页 / 菜单进入；
- 可返回。

建议 Demo 卡类型：

- 食物卡；
- 陪伴卡；
- 装备卡；
- Boss 测试卡或能量卡。

可简化：

- 不做完整商业卡包；
- 不做家园卡；
- 不做宠物卡；
- 不做纸卡玩法；
- 不做赠送完整资产系统，除非 Boss / 联机需要验证。

### 5.7 碰一碰 + BLE 联机

必须做：

- 两台设备进入联机模式；
- 屏幕提示顶部靠近；
- NFC 或近距离触发；
- BLE 建连；
- 显示对方设备或对方宠物的连接成功状态；
- 双方确认后进入合作岩灵 Boss；
- 断线时有提示并安全退出。

MVP-A 可简化：

- 不做完整好友系统；
- 不做完整设备名片；
- 不做多设备；
- 不做远距离发现；
- 不做复杂重连策略。

### 5.8 合作岩灵 Boss

必须做：

- Boss 页面；
- 岩灵 Boss 主视觉；
- 双方进入战斗；
- 简化回合或阶段；
- 至少一种 QTE；
- 双方操作对 Boss 结果有影响；
- 胜利 / 失败 / 中断结果页；
- 结果写入本地或 Demo 状态。

建议流程：

```text
进入合作 Boss
→ 等待朋友连接
→ 双方确认
→ Boss 出现
→ 回合 / 阶段开始
→ 玩家选择或直接 QTE
→ 双端同步
→ Boss HP 变化
→ 结算
→ 奖励 / 结束
```

MVP-A 可简化：

- Boss 时长可短于商业版；
- 可用固定数值；
- 可不实现完整装备加成；
- 可不实现完整掉落奖励；
- 不做匹配；
- 不做排行榜。

### 5.9 本地存档与异常恢复

必须做：

- 当前 Stage 保存；
- 成长进度保存；
- 已读 Demo 卡保存；
- 关键流程状态保存；
- 低电 / 重启后能恢复到安全页面；
- 写入失败有保护；
- Debug 或测试方式可清档 / 快速成长。

建议存档字段：

- save_version；
- device_id；
- current_stage；
- growth_progress；
- pet_state；
- card_bag_demo；
- last_scene；
- boss_result；
- checksum 或简单校验。

## 6. MVP-A UI 范围

### 6.1 必要页面类型

建议页面分组：

1. 启动 / 唤醒；
2. Stage 成长；
3. 首页 / 家园；
4. 喂食；
5. 陪伴；
6. 训练；
7. NFC 读卡；
8. 卡包；
9. 联机等待；
10. 合作 Boss；
11. Boss 结果；
12. 异常 / 恢复；
13. Debug / 测试。

### 6.2 页面设计规则

所有页面应遵守：

- 454×454 主画布；
- 圆屏安全区；
- 顶部短标题；
- 中央主视觉；
- 底部唯一操作气泡；
- 文案短；
- 不做长列表；
- 不做触摸；
- 不做手机式导航；
- 每页只表达一个核心动作。

### 6.3 页面文案风格

建议：

- 面向儿童；
- 短句；
- 有仪式感；
- 不暴露复杂公式；
- 不显示成人化术语。

示例：

```text
发现灵蛋
轻轻唤醒
它饿啦
陪陪它
贴近卡牌
找到朋友啦
岩灵来了
一起守护
能量恢复
保存完成
```

## 7. MVP-A 美术 / 资源范围

必须覆盖：

至少包含：

- idle 静态；
- idle 序列帧；
- happy；
- sleep 或 rest；
- train；
- action / attack；
- static_fallback.png。

### 7.3 工程资源建议

建议资源包包含：

- PNG 序列帧；
- Sprite Sheet；
- animation.json；
- frame_index.csv；
- asset_manifest.json；
- animation_manifest.json；
- copy_cn.json；
- resource_index.csv。

### 7.4 QA 要求

必须检查：

- 图片居中；
- 圆形安全区；
- 无多余白边；
- 透明背景；
- 不串图；
- 命名连续；
- 尺寸一致；
- 小屏可识别；
- QTE 条可读；
- fallback 可用。

## 9. MVP-A 验收标准

### 9.1 演示验收

必须能演示：

1. 设备启动；
2. 灵蛋唤醒；
3. 青龙阶段成长；
4. 首页 4 键操作；
5. NFC 读卡；
6. 卡包展示；
7. 两台设备碰一碰；
8. BLE 进入合作 Boss；
9. QTE / Boss 战斗；
10. 结果页；
11. 重启后存档仍在。

### 9.2 工程验收

必须满足：

- 不破坏 SDK 原有构建；
- 不引入无关依赖；
- 不修改无关板级配置；
- UI 资源路径清晰；
- 页面状态机清晰；
- 按键逻辑可回退；
- 存档有基础保护；
- 异常能安全退出；
- 有测试说明。

### 9.3 CodeX 输出验收

每个 CodeX 任务需输出：

- 修改文件；
- 新增文件；
- 测试方法；
- 未完成项；
- 风险点；
- 后续建议；
- commit message。

## 10. MVP-A 与完整 PRD 的关系

MVP-A 是完整产品的第一阶段工程验证，不等于最终商业版。

完整 PRD 中的以下内容可作为后续参考，但不直接进入 MVP-A：

- 18 只灵兽；
- SD 内容卡商业扩展；
- 设备最多 5 只宠物；
- 宠物卡替代 SD 卡；
- 家园卡；
- 纸卡玩法；
- 完整卡牌概率；
- 完整 1v1 对战；
- 完整奖励和图鉴；
- IP 衍生；
- 商业渠道；
- 投资人 Roadmap。

CodeX 在执行 MVP-A 任务时，必须优先做“能跑通 Demo 的最小闭环”，不要把完整商业版复杂度提前带入开发板 Demo。
